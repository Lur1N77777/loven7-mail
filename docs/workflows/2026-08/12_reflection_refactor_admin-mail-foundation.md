**日期**: 2026-08-12

## 1. 概述

渐进式重构 Admin 邮件工作区的基础架构。将邮件状态规则、缓存协议、状态持久化、远程同步、列表读取和删除请求从大型 React 视图迁移到独立的 domain、application 与 infrastructure 模块，同时把严格 TypeScript 纳入生产构建，并修复已知高危传递依赖。

## 2. 修改内容

- 启用严格 TypeScript，并让 Admin 生产构建先执行类型检查。
- 抽取邮件状态领域规则，统一 inbox/unknown 兼容身份、已读、星标和 read-all watermark。
- 抽取租户隔离的列表与详情缓存，加入版本、身份及损坏数据校验。
- 抽取本地状态存储、跨视图事件、远程状态合并与回填逻辑。
- 抽取邮件列表和删除网关，集中管理端点、请求参数、缓存 TTL 与失效标签。
- 增加 7 组专项测试及结构所有权契约，防止协议重新泄漏到视图层。
- 将 4 条 high 级依赖告警修复为 0，并更新两套应用锁文件。

## 3. 遇到的错误

1. **严格类型检查暴露隐式契约（重要）**：CORS 返回值、联合类型事件、动态索引和 Promise fallback 原先依赖宽松推断。
2. **测试夹具与真实协议不一致（重要）**：发件箱 `raw` 实际是 JSON 字符串，不能按 RFC 822 邮件源构造。
3. **错误的详情层假设（次要）**：初步盘点可能将详情读取理解为远程 GET；实际代码使用列表原始数据和会话缓存。
4. **部署目标名称不一致（重要）**：仓库示例名与 Cloudflare 账号中的实际 Pages 项目名不同，直接使用默认值会部署到错误目标或失败。
5. **锁文件与安装树短暂不一致（次要）**：`npm audit fix --package-lock-only` 后，本地 `node_modules` 仍显示旧传递依赖，必须通过 `npm ci` 重建后再验证。

## 4. 根本原因分析

- 邮件视图同时拥有 UI 状态、业务规则、存储格式和 HTTP 协议，任何一处变化都会扩大回归范围。
- 宽松 TypeScript 允许跨层隐式假设长期存在，生产构建又没有强制执行类型门禁。
- 缓存与远程状态缺少显式端口，导致租户作用域、兼容键和失效规则散落在组件中。
- 部署配置同时存在文档默认值、wrangler 名称和线上项目名，不能仅凭单一来源确定生产目标。

## 5. 调试过程

1. 先收紧 TypeScript 配置，用编译错误定位真实边界缺口。
2. 按领域状态、缓存、持久化、同步、列表和删除六个垂直切片逐步迁移。
3. 每个切片先增加失败测试，再实现最小适配器并迁移调用点。
4. 每轮执行专项测试、Admin 全测、生产构建和仓库级发布门禁。
5. 部署前运行依赖审计、Cloudflare 登录检查、项目列表和历史部署交叉验证。
6. 部署后同时验证不可变 Pages URL、自定义域名资源指纹及 Webmail 运行时探针。

## 6. 经验总结

- 大型视图重构应移动“协议所有权”，而不是一次性搬走整个 UI 状态机。
- 不应为了架构对称虚构不存在的网关；边界必须来自真实 I/O。
- 严格类型检查应属于 build，而不仅是可选 lint，否则本地与发布质量标准会漂移。
- 缓存必须把租户作用域、版本和身份校验作为协议的一部分，不能只封装 JSON 读写。
- 生产部署必须验证实际账号项目、保留 Dashboard bindings，并在自定义域名上做运行时检查。

## 7. 知识提炼

- 可复用模式：Domain 负责纯状态规则，Application 负责合并决策，Infrastructure 负责存储和 HTTP 协议，React 视图只编排交互。
- 可复用模式：使用源码结构测试约束关键协议的所有权，防止后续重构倒退。
- 可复用模式：发布链采用“干净安装 -> 审计 -> 全量门禁 -> 部署 -> 线上探针”。
- 应避免：按文件大小做大规模重写、根据命名猜测接口、把上传成功等同于线上功能正常。
